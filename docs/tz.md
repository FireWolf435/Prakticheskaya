# Техническое задание на информационную систему Service Desk

## 1. Общие сведения

**Наименование системы:** Информационная система учёта и обработки заявок технической поддержки (Service Desk)

**Заказчик:** ООО «Вектор-Пром»

**Разработчик:** [ФИО студента]

**Основание для разработки:** Индивидуальное задание на производственную практику (ПМ.11, ПМ.02)

**Плановые сроки:** 6 недель (42 рабочих дня)

**Стадия разработки:** Опытная эксплуатация

---

## 2. Назначение и цели создания системы

### 2.1 Назначение
Автоматизация процессов приёма, учёта, распределения и контроля исполнения заявок на техническую поддержку в организации ООО «Вектор-Пром» (около 260 сотрудников, около 30 подразделений).

### 2.2 Цели
1. Централизованный учёт заявок с полной историей изменений
2. Автоматическое распределение заявок между инженерами с учётом навыков и загрузки
3. Контроль соблюдения SLA (сроки решения)
4. Интеграция с централизованным каталогом пользователей (LDAP)
5. Почтовая интеграция (создание заявок из писем)
6. Учёт оборудования (CMDB)
7. Формирование отчётности

---

## 3. Требования к системе

### 3.1 Функциональные требования

#### 3.1.1 Организационная структура
- Подразделения образуют иерархию любой глубины
- У подразделения есть руководитель
- Сотрудники привязаны к подразделениям

#### 3.1.2 Заявка
Атрибуты: автор, категория, приоритет, тема, описание, вложения, комментарии, связанное оборудование, исполнитель. Хранится полная история изменений.

#### 3.1.3 Жизненный цикл заявки
| Из статуса | В статус |
|---|---|
| Новая | Назначена, Отклонена |
| Назначена | В работе, Отклонена |
| В работе | Ожидание пользователя, Решена |
| Ожидание пользователя | В работе |
| Решена | Закрыта, Переоткрыта (только в течение 72 ч) |
| Переоткрыта | В работу, Решена |

Любой другой переход запрещён, запрет обеспечивает СУБД.

#### 3.1.4 SLA
- Срок решения в рабочих часах по производственному календарю (9:00-18:00, обед 13:00-14:00, сокращённый день до 17:00)
- Нормативы из `ref/priorities_sla.csv`
- В статусе «Ожидание пользователя» таймер на паузе

#### 3.1.5 Автоназначение
Инженер выбирается с учётом навыков по категории, текущей загрузки и графика дежурств.

#### 3.1.6 График дежурств
Смены одного инженера не могут пересекаться. Гарантирует СУБД.

#### 3.1.7 Учёт оборудования (CMDB)
Инвентарный и серийный номер, ответственный, местонахождение, история перемещений, привязка к заявкам.

#### 3.1.8 Почта
- Письмо на `support@corp.local` создаёт заявку
- Ответ на письмо с `[#номер]` в теме добавляет комментарий
- При смене статуса отправляется уведомление по email

#### 3.1.9 Отчёты
- Просрочки SLA
- Загрузка инженеров
- Среднее время решения по категориям
- Динамика по неделям
- Распределение заявок по часам суток

### 3.2 Нефункциональные требования

#### 3.2.1 Производительность
- Время отклика API: < 200 мс для 95% запросов
- Поддержка 1 000 000+ заявок
- Время выполнения тяжёлых запросов < 1 сек

#### 3.2.2 Безопасность
- Аутентификация через LDAP
- Ролевая модель (9 ролей)
- RLS на уровне строк
- Маскирование чувствительных данных
- Шифрование соединений (SSL/TLS)
- Аудит всех изменений

#### 3.2.3 Надёжность
- Резервное копирование (pg_dump, WAL)
- Восстановление на момент времени (PITR)
- Идемпотентный импорт

#### 3.2.4 Масштабируемость
- Горизонтальное масштабирование через Docker Compose
- Секционирование audit.log по месяцам

### 3.3 Требования к интерфейсу
- Веб-интерфейс (REST API на FastAPI)
- Десктоп-клиент (PySide6, формы .ui из Qt Designer)
- Понятные сообщения об ошибках (без трейсбеков)

### 3.4 Требования к данным
- Исходные данные из 8 источников (кадры, 1С, LDAP, почта, CMDB, заявки)
- Идемпотентный импорт (повторный запуск не создаёт дублей)
- Сверка: строки в файле = строки в staging = загружено + отклонено

## 4. Архитектура системы

### 4.1 Компоненты

| Компонент | Назначение | Технология |
|---|---|---|
| postgres | PostgreSQL 16+: данные, бизнес-правила, безопасность | PostgreSQL 16 |
| ldap | OpenLDAP — каталог пользователей | OpenLDAP |
| mail | docker-mailserver (Postfix + Dovecot) | docker-mailserver |
| core | Доменная логика (Python-пакет) | Python 3.12+ |
| api | REST API на FastAPI | FastAPI |
| notifier | Фоновый воркер: outbox → SMTP | Python 3.12+ |
| mailintake | Забор писем по IMAP, создание заявок | Python 3.12+ |
| dirsync | Синхронизация LDAP с БД и ролями PG | Python 3.12+ |
| importer | Загрузка исходных данных | Python 3.12+ |
| desk-client | Десктоп-клиент на PySide6 | PySide6 |
| ops/ | Скрипты резервного копирования и мониторинга | Bash/Python |

### 4.2 Требования к компонентам
- Секреты не хранятся в репозитории (`.env.example`, Docker secrets)
- Каждый сервис подключается к БД под своей ролью с минимальными правами
- Вся система поднимается командой `docker compose up`

## 5. Модель данных

### 5.1 Схемы
- `ref` — справочники (подразделения, сотрудники, категории, приоритеты и т.д.)
- `core` — предметная область (заявки, оборудование, связи)
- `audit` — журналы (аудит изменений, DDL, безопасность)
- `sec` — безопасность (пользователи, роли, права)
- `stage` — импорт (staging-таблицы, журнал импорта)

### 5.2 Таблицы (21 базовая)
**ref:** departments, employees, locations, categories, priorities_sla, engineer_skills, duty_schedule, production_calendar, ticket_transitions, ticket_status
**core:** tickets, ticket_status_history, ticket_comments, ticket_attachments, ticket_assets, assets, asset_movements, outbox
**audit:** log (секционирована), ddl_log, security_events
**sec:** users, roles, user_roles
**stage:** import_log

### 5.3 Ограничения целостности
- PK, FK с осознанно выбранными ON DELETE/ON UPDATE
- UNIQUE, CHECK, NOT NULL
- Пользовательские домены: email (citext), snils (checksum), inv_no
- EXCLUDE USING gist по tstzrange для дежурств
- Частичный уникальный индекс по СНИЛС

## 6. Безопасность

### 6.1 Аутентификация
- LDAP (OpenLDAP) как централизованный каталог
- Аутентификация почты через LDAP
- dirsync синхронизирует LDAP с БД и ролями PostgreSQL

### 6.2 Авторизация
- 9 групповых ролей: employee, engineer, dispatcher, dept_head, auditor, reporting, app_service, migrator, dba
- RLS на заявках (сотрудник видит свои, инженер — назначенные, руководитель — подразделение и вложенные)
- Колоночные права (reporting не видит СНИЛС, телефон, email, дату рождения)
- Маскирование чувствительных данных

### 6.3 Шифрование
- pgcrypto для СНИЛС и даты рождения
- SSL/TLS для соединений
- Ключи передаются приложением, в БД не хранятся

### 6.4 Аудит
- Журнал изменений (audit.log) с jsonb-диффом
- Событийный триггер для DDL, GRANT, REVOKE
- Маскирование паролей в аудите

## 7. Тестирование

### 7.1 Автотесты
- pytest, не менее 60 автотестов
- 15 интеграционных на настоящем PostgreSQL
- 10 негативных тестов безопасности
- Property-based тесты SLA на hypothesis
- Тесты импорта на контрольных значениях
- Тесты mailintake на каждом письме
- Покрытие пакета core — не ниже 85%

### 7.2 Тестовые сценарии
- Не менее 25 кейсов (предусловия, шаги, ожидаемый результат, фактический результат)
- Сквозной сценарий: письмо → заявка → автоназначение → уведомление → решение → уведомление

### 7.3 Журнал отладки
- Не менее 5 реальных дефектов
- Обязательный дефект 1: два диспетчера одновременно назначают одну заявку
- Обязательный дефект 2: автоответ на уведомление создаёт петлю
