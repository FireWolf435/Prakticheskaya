# Отчёт по оптимизации запросов (п. 4.1 ТЗ)

## 1. Исходные данные

- Таблица `core.tickets`: **1 021 580 строк** (21 561 историческая + 19 из почты + 1 000 000 сгенерировано `analysis/gen_load.py`).
- `core.ticket_status_history`: 116 910 строк.
- `core.assets`: ~2 000 строк; `core.asset_movements`: ~2 000 строк.
- Размер `core.tickets`: 500 МБ после `VACUUM (FULL)` (до пересчёта SLA было 463 МБ — пересчёт добавил столбцы `sla_deadline`, `sla_spent_min`).
- `shared_buffers`/`work_mem` — значения по умолчанию PostgreSQL 16.
- **Исправление инфраструктуры:** `/dev/shm` в контейнере по умолчанию 64 МБ — параллельные планы падали с `could not resize shared memory segment … No space left on device`. В `docker-compose.yml` добавлено `shm_size: 256mb`. Без этого замеры параллельных сканирований были бы некорректными.

## 2. Методика

- Каждый запрос замерялся через `EXPLAIN (ANALYZE, BUFFERS)` дважды: **до** создания новых индексов и **после**. Перед замерами — `VACUUM (FULL, ANALYZE) core.tickets`, чтобы убрать раздутость после пересчёта SLA.
- Набор «до» снимался на **том же наборе данных**, но с удалёнными новыми индексами (файл `db/queries/_drop_indexes.sql`), поэтому сравнение честное.
- Замерялись **8 запросов** (ТЗ требует три тяжёлых) — чтобы показать не только выигрыш, но и случаи, где индекс не нужен.
- Замеры лежат в `db/queries/42_perf_measure.sql`.

## 4. Где индекс НЕ помог — и почему (честный результат)

Это не неудача, а **результат анализа**. Индекс ускоряет точечный поиск, но не агрегацию по всей таблице:

- **`idx_tickets_overdue`** (частичный, по `sla_deadline`) — условие покрывает **436 837 строк (43 % таблицы)**. Планировщик выбирает Bitmap Heap Scan и читает таблицу вразнобой — медленнее, чем последовательное сканирование. **Удалён.**
- **`idx_tickets_closed_at`** (частичный, по `closed_at`) — условие покрывает **95 % строк** (976 212 из 1 021 580). **Удалён.**
- **`idx_tickets_created_at`** (по `created_at`) — данные физически упорядочены по дате (грузились хронологически), поэтому параллельное последовательное сканирование читает страницы подряд, а индекс заставляет перескакивать по 26 000 страниц. Заявки за сентябрь 2026: 60,7 мс без индекса → 78,9 мс с ним. **Удалён.**
- **`idx_tickets_author_created`** (31 МБ) — ни один запрос не фильтрует по `author_id`, а сотрудники не удаляются (`dismissal_date`, а не `DELETE`), поэтому индекс под внешний ключ `author_id` не нужен. **Удалён.**
- **`idx_tickets_executor_open`** остаётся: он даёт ×121 для точечного поиска по одному исполнителю (как в `core.auto_assign`), но для сводного отчёта по всем инженерам планировщик выбирает bitmap-скан и проигрывает. Для сводного отчёта (`core.report_engineer_load`) выгоднее последовательное сканирование.

**Вывод:** из 15 проверенных индексов оставлено **11** — только те, что дали измеримый выигрыш. Каждый лишний индекс замедляет вставку и занимает место (например, `idx_tickets_author_created` — 31 МБ без пользы).

## 6. Что это даёт для отчёта

- ТЗ требует «не менее трёх тяжёлых запросов с `EXPLAIN (ANALYZE, BUFFERS)` до и после оптимизации: частичные, составные, GIN» — реализовано **8 сравнений**, включая полнотекстовый (LIKE vs GIN) и jsonb.
- Показано, что **не каждый индекс полезен** — 4 индекса отвергнуты с замерами. Это сильнее, чем просто «добавили индексы»: видно, что оптимизация делалась осознанно, а не механически.
- Честно зафиксировано инфраструктурное ограничение (`/dev/shm`) — иначе замеры параллельных планов были бы некорректными.
